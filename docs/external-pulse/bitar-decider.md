# Bitar Decider Library

- **Source:** Tweet/thread by Nadeem Bitar (@shinzui), pasted into chat 2026-05-03. URL not captured. Library not yet public ("still a fair bit of work before I'd use it at work").
- **Encountered:** 2026-05-03, in conversation, alongside the user's request "any way I could make business-logic bugs structurally impossible."
- **Verdict:** lane 4 (pattern, primary) + half-day lane 3 spike (single-source-of-truth state-machine refactor on the most drift-prone CLI surface). Library itself is private Haskell — no code-borrow path; pattern transfers.

## 1. Core idea (one sentence, your words)

A Haskell library where each edge of an event-sourced workflow's state machine is declared once via a small DSL (`from State; onCmd Ctor \d -> do; slot @"x" .= ...; emit ...; goto NextState`), so both `decide :: cmd → state → [event]` and `evolve :: state → event → state` are derived from the same definition (and therefore can't drift), with auto-generated Mermaid diagrams and SMT-backed CI invariant proofs that either prove a property over all reachable paths or hand back a counter-example trace.

## 2. Anatomy (load-bearing claims, your words)

Prose source — the post is a design statement, not a shipped library. Claims worth carrying:

1. **Hand-written event-sourced deciders carry one specific bug class: producer/replayer drift.** `decide` produces events; `evolve` consumes them on replay; they are written by hand in two places and silently disagree. Quote: *"decide and evolve quietly drifting out of sync, so a freshly produced event no longer round-trips through replay and invariants are violated."* Missed branches in case-analysis are a related symptom.
2. **Single edge definition + derivation eliminates the drift class entirely.** *"There is no separate evolve. Replay is generated from the same edge definition that produced the event, so the two directions can't fall out of sync."* Compile-time impossibility, not "well-tested."
3. **The same definition powers visualization for free.** Mermaid diagrams generated from the edge declarations — agents and reviewers see what was actually written, not separately maintained docs.
4. **SMT-backed CI proofs catch path properties unit tests can't.** Invariants like *"no path reaches Confirmed without the code-equality guard firing"*, *"every started registration eventually reaches a terminal state"*, *"deletedAt is never set on a non-terminal vertex"* are either proven or returned with counter-example traces.
5. **Pitched explicitly at agent-generated code.** *"I've been building a library that aims to make business-logic bugs almost impossible to ship, even when the code is generated by a coding agent."* Same target failure mode interlinked exists to gate, attacked from a different layer.

## 4. Substrate vs. surface

- **Surface:** Haskell event-sourcing library; user-facing surface is the `from/onCmd/slot/emit/goto` DSL plus a CI command running the SMT proofs.
- **Substrate:** three reusable techniques, language-portable as patterns —
  (a) **Single-source-of-truth derivation.** When two functions must round-trip (producer + replayer; encoder + decoder; check + fix; rule + parity-mirror), declare them via one definition and derive both. Drift becomes unrepresentable.
  (b) **Auto-generated visualization from the source-of-truth.** Mermaid from edge declarations — same shape we already use for `docs/generated/*.md`.
  (c) **SMT/model-checked path properties.** Beyond per-state unit tests, prove cross-state invariants over all reachable paths.

Code is Haskell + private — no code-borrow path. Patterns transfer to TS at varying cost.

## 5. Lane

**Lane 4 (pattern) primary + lane 3 (technique-as-substrate) for the highest-leverage drift-prone surface.**

### Where the technique applies in the CLI today

Mapping Bitar's drift-bug class onto interlinked surfaces, ranked by load-bearing-ness for the user's "structurally impossible business-logic bugs" goal:

1. **Reservation state machine** (`src/harness/reservations.ts`). Three-party state machine: local cache → harness optimistic-grant → remote `ServerApiClient` async-confirm. Acquire / release / expire under concurrency between cohort agents. Invariants ("no two agents hold the same path simultaneously", "every reservation either releases or expires", "expired reservations are reclaimable", "an optimistic local grant that the server rejects is rolled back"). Most load-bearing fit because: (a) genuine concurrency, (b) silent failure mode is double-allocation between agents — the worst kind of cohort bug, (c) three-way drift surface (local / harness / server), more than the two-way Haskell example. **Highest payoff.**

2. **Activity-log replay → session state** (`src/lib/local-activity.ts`). Append-only `activity.jsonl` events; session state in `sessions/{id}.json` is rebuilt by replay. Producer (hook script `.interlinked/hooks/interlinked-activity.mjs`) and replayer (CLI commands deriving session) are written separately. *Closest literal analog* to Bitar's example. Verification needed before claiming the drift exists in current code — the architecture may be one-directional in practice (hook writes; CLI only reads, never re-projects).

3. **Sync cursor + batch sync to server** (`src/lib/local-activity.ts`). Pending → sent → confirmed state machine. Drift bug: cursor advances past unconfirmed events. SMT/PBT-checkable invariant: cursor never advances past unconfirmed.

4. **Check-registry multi-touchpoint coupling** (CLAUDE.md documents 5 touchpoints per new check). Already partially derived via `check-registry/builders.ts`; gated by `__tests__/check-pipeline-parity.test.ts` (regex parity, not derivation). Remaining drift surface is `verify.ts`'s four co-dependent integration points (interface + init + push + streamCqSection — CLAUDE.md says "land atomically via a Node one-shot, not four sequential Edit calls"). Bitar's pattern applied: declare a check ONCE, derive all 5 registrations including verify.ts plumbing. **Documented pain point.**

5. **Hook script generation** (`src/lib/hooks.ts` → `.interlinked/hooks/interlinked-activity.mjs`). Generator + generated artifact. Not a state machine; doesn't fit Bitar's pattern directly. Existing rebuild-on-enable handles drift adequately.

6. **Guard evaluator pattern logic.** Mostly lexical pattern matches, not a state machine. SMT/PBT not the right fit; existing unit tests cover this.

### TS-shaped translation of Bitar's primitives

Haskell type-level state machines don't port; the *spirit* does:
- **Discriminated unions + exhaustive `never`-defaults** for state and event types — TS native, makes "missed branch" a compile error.
- **Builder returning a `{ apply, produce }` pair** — declare each transition once via `transition({ from, on, slot, emit, goto })`; the builder returns matched `apply` and `produce`. Drift becomes unrepresentable because both functions come from one call.
- **Auto-Mermaid generator** — walks registered transitions, emits a `.mmd` file. Same shape as `docs/generated/`.
- **fast-check property-based tests** stand in for SMT for ~95% of the invariants we'd otherwise SMT-verify. Not currently a dependency. Reach for TLA+ / Z3 only when an invariant genuinely needs unbounded reachability proof PBT can't reach.

### Disagreement to record

None. Bitar's framing — *make whole bug classes structurally impossible at compile time, layered with mechanical proofs at CI time* — aligns directly with `feedback_harness_deterministic_only.md` and `feedback_taste_enforcement.md`.

## 6. Smallest spike

**Single-source-of-truth refactor of the reservation state machine + property-based invariant tests — half a day.**

Why this and not session-state or check-registry:
- Reservation has documented state transitions (acquire/release/expire), real concurrency, and the *highest cost-of-drift* of the three (silent double-allocation between cohort agents).
- Session-state needs a verification pass first (does the drift actually exist?) before refactoring is justified.
- Check-registry already has `builders.ts`; that's incremental, not a canonical demonstration.

Spike steps:
1. Define `ReservationTransition` as a discriminated union of `acquire | release | expire | server_confirm | server_reject` with explicit pre/post state.
2. Replace the current logic in `reservations.ts` with `buildReservationMachine([...transitions])` returning `{ applyEvent, produceEvent, transitions }`. Both functions come from one declaration; cannot drift.
3. Add fast-check (new dep) property tests asserting:
   (a) no two agents hold the same path simultaneously,
   (b) every acquire eventually releases or expires,
   (c) expired reservations are reclaimable,
   (d) replay of the event log yields the same state as live execution,
   (e) server-rejection of an optimistic grant rolls back local state.
   Bug class becomes a property failure with a counter-example trace — Bitar's SMT step at PBT cost.
4. Generate a Mermaid diagram of the transitions; check into `docs/generated/reservation-machine.md`.
5. Confirm `__tests__/reservations.test.ts` still passes; the refactor must be behavior-preserving.

If this lands cleanly, follow-ups (each ~½ day):
- **A:** apply the same builder to session-event derivation — but only if step 3's tests reveal a producer/replayer drift worth fixing.
- **B:** extend `check-registry/builders.ts` to derive `verify.ts` plumbing from a single declaration, eliminating the documented "land atomically" coupling.

If the spike *fails* — reservation logic too simple to need a state-machine refactor, or builder ergonomics in TS feel worse than current code — record that and the lane stays at 4 (pattern only, no integration).

## Notes

- **Library not public.** Treat the post as a design statement, not a tested implementation. Re-evaluate if/when it lands; the SMT-checker tooling may be the bigger contribution than the type-level DSL.
- **Pattern-cluster bookkeeping.** Single-source-of-truth derivation is *partially* applied in this codebase already: `check-registry/builders.ts` derives legacy data structures from `CHECK_REGISTRY`; `__tests__/check-pipeline-parity.test.ts` regex-checks parity between `verify.ts` and the registry. Bitar's framing names and generalizes a discipline already partially present. Not a new pattern adoption — a clarifying lens for an existing one, with concrete extension targets above.
- **TS analog ceiling.** Bitar's compile-time impossibility leans on Haskell's GADTs / type-level naturals / `slot @"name"` field-level types. TS reaches "as type-safe as Haskell" only in narrow domains; the practical translation is "the drift class becomes very hard, not impossible." For genuinely unrepresentable drift, the test-time / CI-time layer (PBT, parity tests) covers what types cannot.
- **Mermaid generation as a free subpattern.** Anywhere we add a builder-derived registry, a Mermaid generator drops out. Reservation spike step 4 is the first instance; the same pattern can fold into `docs/generated/` for any state-machine surface.
- **SMT specifically is overkill for this codebase.** Real engineering effort to wire Z3 against TS. fast-check is the cheap right answer for ~95% of the invariants. Reach for TLA+ only when an invariant needs unbounded reachability proof PBT can't reach.
- **Bitar's "even when generated by a coding agent" framing matters.** It places the technique on the *receiving* end of the agent-coding pipeline interlinked occupies the *transmitting* end of: harness gates what the agent writes; type-level / SMT-checked state machines guarantee the result is correct *regardless* of what the agent wrote. Complementary, not competitive.
